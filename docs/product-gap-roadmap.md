## 核心判断

Talk&Talk 已经不是一个“只有原型页面”的产品：登录与法律同意、已审核陪伴者展示、服务商品、结构化可约时段、容量锁定、订单与支付、平台内会话、内容审核、退款/工单/商业结算控制都已有基础。

供给侧的第一道断点已经补上：陪伴者现在可以在小程序自行经营服务商品、结构化时段，并从工作台看到待确认预约和可结算收入。预约后的改期协商、退款申请与售后状态也已能在订单内闭环；服务前后也会基于真实预约时间提示双方下一步并进入订单会话。已支付、未开始的订单还会展示共同的服务前约定，让客户和陪伴者分别确认平台内沟通、服务范围与安全边界，并保留各自确认时间。服务完成后，客户还可以提交一次仅对平台可见的轻量体验反馈；需要介入时明确转入既有订单工单，不把低分、文字或标签暴露给陪伴者，也不自动改变退款、结算或订单状态。真实订单参与者现在也可在本人尚未关闭的订单问题/退款工单中，补充一段仅客服可见、限长且不可编辑的时间、履约或支付事实；它不复制聊天、不接受附件、不让另一方读取，明显的身份、联系方式、证件或健康/医疗材料会在入库前被拒绝，也不自动改变退款、结算或订单状态。客户还可从完成订单回到同一项服务的实时可约日历，但旧时间、旧价格和旧上架状态从不被复用。公开资料页已把当前展示核验、非医疗边界和下单时再次锁定说清楚；客户也能将仍公开的对象保存为仅自己可见的书签，陪伴者看不到收藏关系、数量或通知。发现页现在还可按名称、角色、公开服务标签或当前上架服务标题提交关键词搜索，也可按当前上架服务的主题、文字/语音方式和单次总价上限显式缩小公开结果；多个服务条件只会命中同一项当前上架服务。用户还可只看三天内存在结构化、未满额候选的对象；旧版自由文本时段不会被伪装成真实容量，详情页和下单时仍会再次校验。客户还可主动按在线状态、评分、评价量、每 30 分钟公开标价，或同一匹配服务最早的结构化剩余容量排序；“最早可约”默认只看未来七天或已选更短窗口，不返回或保留时段，详情页和订单会再次校验。上述搜索、筛选和排序不会把私有书签、最近浏览、聊天、订单正文或敏感画像带入结果，搜索输入也不会被保存为行为历史。客户打开公开资料后还会得到一份仅自己可见、最多 20 条的最近浏览回看清单；它不通知陪伴者、不进入推荐或营销，也不代表当前仍可约。客户还可从“我的”进入安全与支持，了解展示核验、平台内边界、举报/复核、订单售后与紧急退出的真实路径；该页面不收集内容、不代为操作，也不承诺报警、救援或人工响应时限。具体聊天页还把已有举报、离开会话和安全说明放到顶部的安全栏；所有动作仍由用户主动触发。真实会话参与者现在还可只为自己建立或解除会话级拉黑：任一方拉黑后，双方都不能继续普通收发或展示该会话历史，本人仍能看到管理入口，另一方只看到不指向任何人的通用不可用状态；它不通知对方，也不取消订单、退款、结算、举报、客服或安全升级路径。广场中已登录用户现在还可针对自己当前可见的一条已发布帖子主动提交限长举报原因；同一人对同一帖子只保留一张私有回执，公开帖子与原因只进入既有受控审核案件，不给作者自动处罚、案件状态或处理时限承诺。提交者还可在广场的私有区域回看最近 50 条仅含提交时间和“已收讫”的回执；它不加载帖子、作者、理由或案件，也不暗示风险已经处置。不同用户对同帖的后续线索现会在帖子与案件双锁内附着至同一个未结案件，并保存各自受控证据；若管理员已结案则安全地开启新案件，不扩大任何用户侧可见性。单账号在十分钟内的新帖子和新举报也会在用户行锁内被频控，同帖重复举报仍可无配额地读取原回执；超限只得到泛化提示，不被写成账号或内容处置。当前下一处真正的体验断点是陪伴者的当日服务清单：已有工作台能看待确认和收入，却还缺按真实预约时间组织今天该做什么的界面。

> 2026-07-21 更新：上一段所述的“陪伴者当日服务清单”已经完成。工作台会从服务端取得以 `Asia/Shanghai` 当天 `[00:00, 24:00)` 为边界、按预约开始时间排序的本人服务条目；每条只含服务名、预约时间、时长与既有订单状态，并回到既有订单页处理。该只读清单不创建日程/提醒、不自动开始或完成服务、不改变结算，也不携带客户、会话、退款、支付或后台字段。

> 2026-07-21 更新：收藏对象的“可约提醒”现已完成**授权与偏好**这一层：客户只能对自己仍收藏、且仍通过当前公开资格校验的资料开启或关闭；开启必须绑定同一账号当前未消费、由明确微信提示产生的一次订阅授权，关闭不再要求授权。偏好和授权令牌均不向陪伴者、公开资料、推荐或订单暴露；系统只向客户端回传开关、更新时间和“同一对象最多每 24 小时一次”的上限。这个阶段不会扫描空档、创建提醒任务、排队、投递或承诺触达，下一阶段仍需单独做真实可约变化的判定和一次性授权的消费。

> 2026-07-21 更新：真实可约变化的第一步也已完成：陪伴者本人新建未来的结构化时段，或把未来的已停用时段重新启用时，系统会在同一事务中，仅为仍公开、仍保存且提醒偏好开启的对象创建去重的内部候选记录。当前候选只要求该时段处于启用状态且配置容量为正，记录只保留书签、陪伴者、时段及该时段版本的引用和生成时间；不读聊天、订单正文或画像，不返回给任一用户，也不是通知任务或投递记录。普通编辑、停用、过期/无配置容量时段不会创建候选；后续阶段仍需重新验证一次性授权、实时容量和 24 小时频控后才能考虑发送。

> 2026-07-21 更新：候选使用前的**实时预检与频控决定**现已完成。服务端在一个事务内先锁定候选，并在后续条件仍需检查时锁定书签、绑定授权和时段，重新确认书签偏好与公开资格、同一账号未消费的绑定授权、候选所指时段版本仍启用，以及当前上架服务和真实预约占用下还存在可订时间；同时按每个书签上一次成功发送时间实施至少 24 小时频控。结果只持久化为不可见的“可投递”或泛化“跳过”原因与时间，不读取聊天、订单正文、客户资料或资金字段，不消耗授权、不创建通知/消息、不调用微信，也不改变订单、日程、书签、推荐、退款或结算。真正投递前仍必须再次校验并在同一安全边界内消费授权。

> 2026-07-21 更新：预检为“可投递”的候选现在可被服务端幂等地转交为一条一对一的**内部交接记录**。交接记录只引用候选并保存创建时间；候选行锁和数据库唯一键共同防止并发重复，`pending`、`skipped` 或没有完成时间的候选均被拒绝。它不是通知、投递、排程、接收人或微信调用记录，不读聊天、订单正文、客户资料、授权内容或资金字段，也不消耗授权、不更新成功发送时间、不启动扫描或 worker；真正的下游消费者仍须最终重检。

> 2026-07-21 更新：一个有界、仅服务端调用的**预备协调器**现在可以一次读取最多 100 个候选 ID：它顺序调用既有预检，并且仅为 `eligible` 结果建立既有交接；`skipped` 只计数，扫描后被级联删除的候选安全忽略，其他异常不会被吞掉。查询会补捞“已预检通过但尚未交接”的候选，以支持中断恢复；它没有控制器、定时器、生命周期钩子、队列生产者或 provider 依赖，因此不会自行扫描、触达、消耗授权、创建消息/通知或改变订单和资金状态。

> 2026-07-21 更新：预备协调现有一个**默认关闭、显式配置才启用**的内部 runner。启用后它才以 15–3600 秒间隔、每次最多 100 条的上限调用协调器，跳过并发重入，并且只记录扫描数、可投递数、跳过数、交接数、已交接数和消失数等聚合日志；关闭时不建定时器、不调用协调器。runner 不依赖通知表、微信或任何 provider，仍不消费授权、不创建用户可见消息/通知、不读取候选/用户明细到日志，也不改变订单、日程、书签、推荐、退款或结算。

> 2026-07-21 更新：每条内部交接现在还能进入一次**实时再校验闸门**。它锁定交接引用后，复用首次预检的同一套候选、书签、授权、时段、上架服务和真实预约容量规则，并要求源候选仍是已完成的 `eligible` 预检；它不复用旧结果。通过时只在内存中返回候选、书签、用户、绑定授权、陪伴者和时段的最小 ID，失败时仅返回泛化原因；不写回候选、不保存准备结果、不消费授权、不创建消息/通知或调用 provider。真正发送仍须把最终重检和授权消费放进同一原子边界。

> 2026-07-21 更新：通过实时再校验的交接现在可在**同一事务**内创建一条一对一、可恢复的私有授权预留尝试：锁顺序为交接、候选、书签、授权、时段，尝试仅关联交接与准确授权并处于 `reserved` 状态。交接和授权各有唯一键，重复调用返回原尝试；若授权已被另一私有尝试占用，只得到泛化不可用结果。开启提醒偏好也会在书签→授权锁内重查该授权没有预留，因此不会与并发预留重新绑定。书签、候选/交接或授权被删除时，关联预留会随其级联清理，避免账户清理被私有恢复记录阻塞。预留不写 `consumedAt` 或 `consumedByDeliveryId`，不更新发送时间、不建通知/消息、不调用微信或 provider；后续发送仍需自己的最终原子重检、消费和结果恢复。

> 2026-07-21 更新：预留尝试现有一个**最终消费与恢复状态机**，但仍没有 provider 调用。服务端只在同一事务内按尝试、交接、候选、书签、授权、时段锁序再次实时校验，且当前绑定授权仍与尝试完全一致时，才写授权 `consumedAt` 并把尝试推进到 `readyToSend`，同时发出只在内存交给未来发送器的短租约。它不会写 `consumedByDeliveryId`、发送成功时间或任何用户消息。活跃租约不会重放令牌；过期或缺失租约只进入 `uncertain`，绝不自动重新消费、重新授权或声称已送达。通用通知投递池会排除已被提醒偏好绑定或私有尝试预留的授权，避免越过该边界。此阶段不建 controller、worker、队列或 provider 调用。

> 2026-07-21 更新：持有 `readyToSend` 租约的内部尝试现在可通过既有微信 provider 进行**一次受保护的发送与结果确认**。服务端先把尝试原子推进到 `sending`，再在事务外调用 provider；确认接受才写 `sent`、provider 消息号，并在同一事务内更新该书签的最近成功发送时间。明确跳过、明确拒绝、确认尚未发出的失败与可能已尝试但结果未知会分别写为私有终态，后者一律为 `uncertain`；租约重入、超时、进程崩溃或最终写回竞争均不自动重发、更不误报成功。发送只使用通用“查看当前可约时段”文案和最小授权身份，不创建小程序内通知、聊天消息、控制器或 worker，也不改变订单、日程、推荐、退款或结算。

> 2026-07-21 更新：真实投递现有一个**默认关闭、部署端显式开启**的内部 runner。它还要求微信订阅通道及 `availabilityReminder` 模板已配置，启动时才以 15–3600 秒间隔、每次最多 100 条执行；同一实例不会并发重入。每一轮先在总批量预算内只隔离已过期或缺失租约的 `readyToSend`/`sending` 尝试，再只读取 `reserved` 尝试，顺序调用最终消费服务，并且仅对本轮刚取得的内存租约立即调用既有发送服务。它不扫描或重发有效旧租约、`uncertain`、`rejected`、`failedBeforeSend`、`sent` 或 `skipped`，日志和指标也只记录聚合数量、不含尝试、用户或授权明细；没有 HTTP 控制器、通知表、聊天消息、队列或新的用户侧结果，并且不改变订单、日程、推荐、退款或结算。

> 2026-07-21 更新：可约提醒的**上线准备与异常运营边界**已补齐。部署预检只有在开关显式为 `true` 时才强制微信订阅通道、`availabilityReminder` 模板和 15–3600 秒/1–100 条边界；默认关闭不会增加商用放行要求。受控放行文档规定先在 staging 用最小真实授权链路演练，再由内网采集仅含聚合的成功、失败和跳过指标；出现 failure 或私有 `uncertain` 时只能暂停 runner、保全证据并用只读聚合状态人工核查，绝不通过释放授权、改写状态、重启或打开 runner 补发。

> 2026-07-21 更新：陪伴者高频排班的**数据基础**已补齐。服务端现可在陪伴者行锁下保存固定 `Asia/Shanghai` 时区的每周规则（周日到周六、当天半小时边界、容量、启停）和无原因文本的一次性停用区间；活跃同星期规则、活跃例外分别拒绝重叠，例外要求明确时区、半小时边界、未来开始且最长 31 天。数据库还以检查约束和级联外键守住周序、分钟、容量、时区与时间范围。

> 2026-07-21 更新：已为**已认证资料所有者**补上私有周期规则与例外的读取、新建、停用 API；每个列表最多 200 条，并只回传本人配置所需字段。新建规则/例外始终是上海时区下的活跃规划输入，停用可幂等执行且保留历史。所有权、资料核验和账户状态会在每次操作前重查；跨陪伴者 ID 只得到通用不存在结果。该 API 不读写客户侧路径，不自动调用 14 天草稿生成器，不启用/删除草稿或单次时段，不改订单、公开可约、收藏提醒、通知或外部日历。

> 2026-07-21 更新：周期规则已有一个**仅内部手动调用的 14 天草稿生成器**。它以“规则 ID + 上海本地发生时刻”作为数据库唯一来源，锁定陪伴者后读取活跃规则、例外、所有既有时段和有效订单占用；只新增完全不冲突的 `isActive=false` 单次时段草稿，重复运行或并发来源键竞争都不会重复创建。黑名单、人工时段、旧草稿和订单覆盖只会让对应发生时刻安全跳过，生成器从不更新、删除或启用任何既有窗口，也不创建提醒候选、通知、controller、定时器或客户可见可约。

产品定位应保持为“女性友好、平台内履约、边界清晰的线上陪伴服务”，而不是直接变成陌生人社交广场或医疗/心理治疗平台。后两者分别需要完全不同的风控、资质与运营能力。

## 交付策略：按闭环，而非按页面堆叠

```text
供给商品管理 API
    → 供给可约时段 API
        → 陪伴者工作台
            → 改约 / 取消 / 履约体验
                → 找人、收藏、复购
                    → 社区互动与主题沉淀
                        → 运营数据、实验、发布门禁
```

## 必须并行推进、但不能靠代码替代的外部门槛

以下不是“以后再说”的功能需求，而是开放真实付费流量前的硬前提；现有仓库的 [商用放行方案](./COMMERCIAL_RELEASE.md) 已列出更完整的证据要求：

- 由合资格主体确认产品为线上陪伴而非医疗/心理治疗，并核定服务话术、未成年人规则、退款/投诉与数据处理边界。
- 用真实 KYC、签约、税务和收款证据完成陪伴者准入；代码中的引用字段不能代替核验本身。
- 为自伤、人身危险、急性医疗等场景建立服务地区可用的人工值班、升级联系人、紧急资源和演练记录；自动审核或风险提示不能等价于救助。
- 真实小程序 AppID、商户、回调、隐私配置、域名和真机支付/退款/通知链路完成隔离 staging 验收。

## 明确后置的能力

订单级 TRTC 语音的代码路径、关房控制和最小出席事实已经交付，但在主体类目、CAM、回调和两台真机证据齐全前保持关闭。仍明确不进入当前开发队列的是：陌生人群语音房、AI 伴侣、临床心理测评或诊疗、复杂协同过滤、会员虚拟币体系和外部社交导流。这些能力会放大供给质量、内容治理、隐私和合规风险，不能因为竞品存在就视为首发缺口。

## 衡量是否真的补齐

每个目标上线前后都需要看同一组可解释指标：

- 供给：完成“服务上架 + 时段发布”的陪伴者占比、未来七天可约时段数、时段利用率。
- 成交：资料页到选服务、选时段到创建订单、确认到支付的转化；失败必须区分无供给、满额、支付、规则和技术错误。
- 履约：按时确认率、改约率及原因、取消率、开始/完成率、退款和工单率。
- 信任：举报率、审核命中/误伤复核、工单首响和结案 SLA、拉黑后的重复骚扰率。
- 留存：完成首单后的再次预约、收藏转化、主题内容到有效预约的转化；不以聊天时长或情感依赖作为核心 KPI。
