# Talk&Talk 商用界面市场交叉审查

审查日期：2026-08-01  
资料口径：截至审查日可访问的官方应用商店、官方帮助中心、官方协议和微信支付商户文档  
审查对象：当前工作区的微信小程序、NestJS API、商业运营后台 `/admin/`、独立审核工作台 `/review/`

## 结论

**第二轮终检仍发现 3 个 P0、5 个 P1 仓库缺口；在它们修复并回归前，仓库闭环与真实商用均为 No-Go。**

第二轮交叉审查没有发现需要复制成新业务线的遗漏，但发现若干“后端已有、正式入口不完整”、账号处置无申诉、队列截断或“错误被伪装为空状态”的问题。支付投诉用户入口已在终检期间补齐；只有下表其余八项清零后，才能重新判定仓库闭环。

即使八项全部修复，仓库也只能证明页面、接口、权限、状态机和失败关闭；它不能证明微信已经审批、真实 KYC 已完成、两台真机 TRTC 可用、人工审核/客服/危机值班已经在岗、生产备份能恢复、真钱支付退款结算已经对账，或无障碍已经通过真机辅助技术测试。上述任一外部 P0 无证据时，仍不得开放真实付费流量。

### 终检仍需清零的仓库缺口

| 级别 | 缺口 | 当前证据 | 完成条件 |
|---|---|---|---|
| P0 | 内容处置申诉只能看已提交记录，刷新或从通知回来后缺少“可申诉案件 → 创建申诉”的稳定入口 | `pages/safety` 只查询已提交申诉；通知未携带可恢复的 `caseId`；后端缺少本人可申诉案件列表 | 增加受保护的本人可申诉案件接口和稳定入口，通知/刷新后仍可提交一次申诉，并覆盖 smoke |
| P0 | 普通用户被限制或封禁时，没有正式处置记录、通知和申诉闭环 | 管理后台可直接切换 `active/restricted/banned`；服务端只改账号状态、撤销令牌并写审计，没有面向用户的理由、政策版本、申诉截止、`AccountAction/Appeal` 或非原处置人复核；全仓现有账号申诉只覆盖陪伴者 | 新增普通用户账号动作与申诉模型；提供 locked-account 最小壳和受保护入口，展示理由/规则/截止，服务端强制非原处置人复核并通知结果 |
| P0 | `banned` 账号的数据权利自助被完整资料请求挡住 | guard 拒绝 `GET /me`，而 `pages/account` 先强依赖 `fetchMe`，失败后整页只显示错误，导致访问/导出/更正/删除请求及其状态不可达；个人页底部另有不依赖 `user` 的撤回/注销按钮，不能把问题夸大成全部法定入口失联 | 将普通资料与数据权利分区加载；`banned` 仍不能恢复普通业务，但可进入政策允许的最小数据权利入口 |
| P1 | 用户没有注销申请状态、截止时间和处理结果查询 | 当前只有创建删除申请接口；注销后可重新微信登录，但没有持久化的本人查询闭环 | 增加最小化本人状态接口和页面，显示状态、法定/承诺处理期限与结果，不暴露内部备注 |
| P1 | 陪伴者账号处置申诉可由原处置人复核 | 账号动作记录 `createdById`，复核尚未拒绝同一 actor | 服务端强制非原处置人复核，并补充单测和界面说明 |
| P1 | 管理退款队列固定最多 200 条，缺少 total/游标或分页 | 管理列表使用固定 `take: 200` | 提供稳定分页与总量/下一页信号，后台可遍历全部待办 |
| P1 | 注销管理界面固定只读第 1 页 50 条，后续待办不可操作 | `/admin/` 请求固定 `page=1&pageSize=50`，界面无翻页控件 | 显示总量/当前页并可前后翻页；筛选变化回到第 1 页，失败不清空成“无待办” |
| P1 | 订单时间线、陪伴者服务单和客服案件加载失败会被吞成空列表 | 客户端 catch 后写空数组 | 分别展示“加载失败/未知”和重试，不把系统故障说成没有记录 |

终检期间已经关闭 1 项：微信支付投诉本人状态已进入订单详情和客服中心，按当前订单或本人全部记录展示；`503` 单独显示“状态未知”，不冒充空列表，并明确正式发起、最终状态和继续反馈均以微信账单为准。小程序 TypeScript、28 页面结构校验、603 次 API 调用 smoke，以及支付模块 9 个测试套件/86 项测试已通过；真实商户通知、回复和完结仍是外部门禁。

## 审查方法和证据等级

1. 先把同类产品拆成四组：国内陪伴/倾诉、全球同伴支持、远程预约服务、双边交易与微信支付治理。
2. 只把官方页面能直接支持的内容记为“市场事实”；应用商店自述和供应商自述仍标明为自述，不当作独立质量认证。
3. 再判断该机制是否适用于线上成年陪伴，而不是按页面数量照搬。线下上门保险、课程录像、未成年人模式等不能机械复制。
4. 最后逐项对照当前磁盘源码、契约、迁移和界面；“有接口无入口”“有回执无进度”“客户端自报替代可信证据”都不算闭环。
5. 状态只使用五类：`仓库闭环`、`仓库缺口`、`上线门禁`、`刻意不复制`、`待最终回归`。上线门禁不能用 Mock、环境变量、截图稿或口头承诺替代。

## 刻意不复制的市场做法

- **不拆两个消费者安装包。** 松果使用独立倾听者 App 是其供给运营选择；Talk&Talk 在同一小程序内做清晰角色工作台，不构成功能缺口。
- **不默认录音。** Cambly 的课程录像适合语言课程回看；情绪陪伴应采用最小出席元数据，除非未来完成单独的法律依据、明确同意、加密、留存和删除设计。
- **不宣称保险、AirCover 或无条件平台担保。** Rover、TaskRabbit、Airbnb 涉及线下财产/人身风险；Talk&Talk 当前只能承诺公开规则、证据审查和真实渠道退款状态。
- **不补未成年人模式。** 当前产品边界是成年用户和成年陪伴者；正确动作是年龄门槛、真实核验和误入处置，不是新增青少年流量。
- **不做礼物币、财富榜、付费认证或付费排名。** 这些机制会增加资金、诱导消费和信任失真风险，不是商用闭环的必要条件。
- **不把 AI 当危机处置人。** 模型可以做失败关闭和分流提示，不能代替地区紧急资源、人工在岗、升级联系人和演练。

## 最小放行实验

最终 Go 之前至少保留以下可复核证据，而不是只勾选清单：

1. 两个真实成年账号和一个真实陪伴者完成“同意 → 需求/筛选 → 下单 → 接单 → JSAPI 支付 → TRTC 履约 → 评价/售后”的完整录像和服务端审计链。
2. 分别演练支付回调丢失、支付结果未知、退款结果未知、消费者投诉重复通知/丢失、用户继续投诉，核对微信权威结果、SLA、冻结、追偿和站内状态。
3. 分别演练陪伴者迟到、用户迟到、双方无出席、弱网重连和客户端伪造心跳，确认可信证据优先、不同人员复核、退款成功不早于微信成功。
4. 用非原处置审核员完成一次内容申诉；用不同供应人员完成一次陪伴者账号动作申诉；检查本人界面显示截止、处理中、逾期和结果。
5. 用限制账号完成数据导出、撤回同意和注销申请；验证受保护下载不可被他人访问，交易/审核法定留存没有被误删。
6. 用微信真机辅助技术、200% 字体/系统缩放、弱网和低端机走完支付、举报、争议和数据权利关键路径，记录缺陷和复测证据。
7. 在不接触真实用户的演练环境执行危机升级：确认页面不会承诺救援，客服能快速定位经法务确认的地区资源、值班联系人和交接记录。

## 最终判定规则

- **仓库闭环通过**：正式入口可达，真实 API 状态可见，错误不会显示成空/成功，权限和申诉独立性可由自动测试与人工抽查证明。
- **生产 Go**：仓库闭环通过只是必要条件；上表全部 P0 有责任人、时间、原始证据和复核签字，且生产 smoke 与受控真钱/真机实验通过后才能决定。
- **当前判定**：八项仓库缺口尚未清零，仓库闭环为 **No-Go**；即使修复，外部 P0 未提供前生产放行仍保持 **No-Go**。
