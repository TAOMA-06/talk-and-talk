# Talk&Talk 正式商用方案与放行门禁

本方案把“代码达到可商用控制强度”和“企业已经获得对外经营资格”分开验收。仓库负责前者；经营主体、微信审批、税务选择、真实证据和生产运维必须由责任人签字确认。只有两层同时通过，才可把 `COMMERCIAL_RELEASE_MODE` 切换为 `commercial` 并开放真实付费流量。

本轮唯一消费者发行面是微信小程序，普通用户与陪伴者在同一小程序内使用角色化界面；商业员工使用 `/admin/`，独立审核部门使用 `/review/`，权威 API 为 NestJS `/api/v1`。`frontend/ios`、消费者 Web 和本地演示不参与商用放行。当前市场交叉审查、仓库红线及刻意不复制项见 [商用界面市场交叉审查（2026-08-01）](./commercial-market-cross-audit-2026-08-01.md)。

## 商业交易模型

1. 陪伴者先完成实名核验，再录入仅含受控外部引用的商业档案：身份核验证据、服务协议版本与签署证据、税务档案、结算收款对象。录入人与复核人必须不同；重新提交或暂停商业档案会自动下架，恢复后仍须单独重新上架。
2. 用户下单时，服务端计算价格、平台费和陪伴者应结金额，并把陪伴者展示信息、身份核验证据引用、服务协议版本及签署证据引用、税务档案引用和收款对象写入订单快照。后续改名、换 owner、重签协议或换收款对象不能改变已成立订单。
3. 陪伴者在响应时限内确认后，用户才可支付。服务启动时先验证商户签名能拉取并解密当前微信平台证书。预下单会先提交唯一 `outTradeNo` 和本地支付保留，再调用微信；请求超时不会武断创建第二笔交易。后台按到期记录查询微信权威状态，回补成功交易或确认关单，并把过期未决支付纳入商用门禁。微信支付回调校验签名、AppID、商户号、金额、币种和交易绑定；订单、支付、审计、站内通知及外部投递意图在同一事务中落库。
4. 服务只能在预约窗口内开始，完整服务时长届满后才能完成。用户可主动确认完成；不确认则在售后窗口届满后视为自动验收，但主动确认不会缩短售后期限。
5. 创建订单时把已经批准的 `REFUND_POLICY_VERSION` 和当时的 `REFUND_REQUEST_WINDOW_HOURS` 固定为不可变订单快照；生产默认方案为 72 小时，但运行时配置只能影响新订单。小程序在支付按钮附近显示该订单的确切小时数、规则版本、服务前/服务中/完成后边界、超窗客服入口和协议链接；快照缺失或非法时禁止支付。订单完成时只用订单快照计算 `refundRequestDeadlineAt`，退款与结算也只认该快照和精确截止时间，不回退到当前配置。窗口关闭后用户仍可提交订单工单，当前工单负责人可基于证据发起例外退款，但必须由另一名管理员审核。退款审核队列、批准、拒绝和重试仅对 `admin` 开放，内容 `moderator` 无资金处置权。结算最早可用时间必须至少比退款窗口晚 24 小时，示例为 96 小时。所有未终结退款（包括支付渠道失败）、未结工单和退款后追偿都会冻结结算。
5a. 微信支付消费者投诉 2.0 使用独立回调 `/api/v1/payments/wechat/complaint-notify`：先验签并以 APIv3 密钥解密，再只持久化通知标识、动作、短摘要和不可逆摘要；不保存回调密文、明文原包、用户手机号或 openid。通知可能重复或丢失，因此 worker 同时查询近三日列表并按投诉号查询权威详情。一个投诉内的全部渠道投诉订单均逐条保存；只有商户单号、微信交易号和金额同时匹配才绑定本地支付，任一订单未关联时禁止完结。次日结束前首次回复、第三日结束前完结均进入后台 SLA；所有匹配订单的未付款收益都会冻结，已经付款或已有转账证据的收益分别生成追偿。商户回复、完结和主动同步都有岗位权限、固定行锁顺序、幂等键和审计；渠道结果未知时禁止重复提交。小程序必须让当事用户看到与本人关联的全部订单及权威状态、SLA 和沟通摘要，不得泄露同一投诉内其他用户的订单；加载失败时不得显示成“没有投诉”。
5b. 付费预约的迟到、未出席与技术故障使用独立履约争议：预约开始并经过公开 10 分钟等待期后、售后 7 日内可立案，立案立即冻结结算。腾讯 TRTC 原始请求体以控制台独立回调密钥做 HMAC-SHA256 验签，只保留进退房、断线重连、音频起止的时间与参与角色；不保存录音、IP、终端类型或设备指纹。客户端进房、心跳和断线事件只能辅助，不能单独裁决。双方依次获得事实补充、答辩和申诉答辩窗口；首轮裁决人与申诉复核人必须不同。终局全额退款进入现有真实退款交易与第二人执行核验，财务不能推翻终局案件结论，且只有微信渠道确认 `success` 才能对用户宣称退款成功。
6. 人工结算执行“领取任务 → 按订单收款快照带外付款 → 录入唯一流水、准确金额、收款对象及凭证 SHA-256 → 另一名管理员复核”。领取后若确认从未转账，必须由另一名管理员凭未转账证明释放，原领取人不能自撤。若退款发生在确认付款后，系统生成陪伴者追偿台账；若发生在领取任务后、付款凭证落库前，则生成“外部付款状态不确定”台账。两者都会冻结后续结算，直至另一名管理员复核回款或未转账证明。

退款的不确定结果处理遵循[微信支付退款最佳实践](https://pay.wechatpay.cn/doc/v3/merchant/4014959631)：先查单，确认退款不存在后才使用原商户退款单号和原参数重试。仓库实现的是该原则的持久化恢复机制；上线验收仍须以届时微信商户平台文档和真实商户返回为准。

日账单实现遵循微信支付官方的[申请交易账单](https://pay.wechatpay.cn/doc/v3/merchant/4013071227)、[申请资金账单](https://pay.wechatpay.cn/doc/v3/merchant/4013071235)与[下载账单](https://pay.wechatpay.cn/doc/v3/merchant/4013071238)约束：下载 URL 具有短时效，下载响应本身不带平台签名，必须校验申请接口给出的 SHA-1。生产仍须用真实商户逐日核对账单格式、可用时间与差异 SOP。

## 仓库已经实施的硬控制

- 陪伴者商业档案双人复核、自动下架和订单级收款/税务/协议快照。
- 退款规则版本与窗口在订单创建时写入数据库不可变快照；重复 `clientRequestId` 在规则配置变化后仍返回原订单及原快照。数据库约束和触发器禁止改写快照，并要求已完成订单的截止时间精确等于 `completedAt + refundRequestWindowHoursSnapshot`。商用模式只有在 `REFUND_POLICY_APPROVED=true` 且存在非秘密批准引用时才能创建新订单；快照缺失、非法或与截止时间不一致会同时阻止支付、退款资格判断、结算和商用放行，任何路径都不回退到当前配置。失败退款持续冻结；普通用户不能重新提交失败退款，管理员重试有独立审计。退款提交前先持久化唯一 `outRefundNo`；进程退出后 worker 会恢复未提交记录，对结果不确定的记录先查询微信，只有微信权威返回 `RESOURCE_NOT_EXISTS` 才以完全相同的退款号和金额重提。查询时间、次数和递增退避持久化到数据库，多副本以数据库租约抢占，避免重启丢任务或并发重复提交；超时记录同时进入后台队列。付款后退款生成独立追偿账。
- 微信 T+1 日账单按上海时间 10:00 后，从显式 `WECHAT_DAILY_BILL_RECONCILIATION_START_DATE` 起为每个应核日期建立 `tradeAll`、`fundBasic`、`fundOperation`、`fundFees` 四类独立运行；自动拉取最多覆盖微信可取的最近 90 日，但更早的配置内缺口不会被静默抹掉，仍会持续阻断放行并要求人工取得账单证据。下载地址只允许微信官方主机和账单路径，禁止重定向，并先验证微信返回的 SHA-1 再解析。应用只保存对账所需的交易引用、资金业务名称/类型、金额、状态、渠道原始事件时间和行摘要，不保存账单原文、openid、商品名或银行字段。支付 `providerPaidAt`、退款申请/受理时间 `providerRefundAcceptedAt` 与退款成功时间 `providerRefundSucceededAt` 只能来自微信权威查询、创建结果或回调；成功时间不得早于申请时间，任一必需事实缺失时失败关闭。既有缺失值作为明确商用 blocker，不能用本地 `updatedAt` 或账单日期猜测。交易账单和 BASIC 资金账单均做本地到微信、微信到本地的反向覆盖；资金金额、账户、收支方向、业务绑定和本地结算状态必须精确一致，手续费及未知资金类型必须形成 critical 人工核验项。支付/退款回调先以 `UNCLASSIFIED` 追加不可变现金台账，渠道、来源、方向和金额不可改写；账户及预计出现的单日资金账单只能由一人提案、另一人批准。`noStatement` 对四类账单都会检查渠道时间范围内的本地活动，不能冒充已核对。差异由当前 finance 负责人提交带受控引用和 SHA-256 的不可变解决提案，必须由另一人复核；接受例外只允许不同的 admin 批准。所有历史开放/调查中差异、待复核提案、未分类现金、覆盖缺口和渠道时间缺失都会继续阻断 `/admin/commercial/readiness`。
- 超过签名账单 API 90 日窗口的缺口只允许通过微信商户平台官方导出补证；账单日不得早于商户平台五年历史窗口。虽然平台可合并最多 31 日，本系统仅接受一个上海自然日、最大 20 MiB 的 CSV。服务端重算原文件与归一化 SHA-256，原文只在请求内解析并立即丢弃；批准人与提交人必须不同，批准事务会锁定提案并禁止并发追加或摘要漂移。拒绝记录保留审计后，可用同一官方内容重新提交修正提案。
- 金融状态、关键审计和通知 outbox 的事务一致性；微信模板授权快照实际 `templateId`，配置换模板后旧授权不能被挪用。
- 微信投递请求 15 秒超时，小于 worker 租约；多副本以数据库 `SKIP LOCKED` 有界领取，provider 调用在短事务外执行，只有持有当前租约的 worker 才能记录成功指标。关闭 worker、到期积压、失败投递和过期租约均是独立 readiness 事实，不能因为站内通知存在就把微信结果改写成成功。
- 收藏对象可约提醒的真实投递 runner 默认关闭；只有 `AVAILABILITY_REMINDER_DELIVERY_ENABLED=true`、微信订阅通道和已审批的 `availabilityReminder` 模板同时满足时才可启动。候选 fanout、准备、授权预留和投递分别使用持久 claim/lease、失败计数与退避；provider 仍在事务外调用。`failedBeforeSend`、`rejected`、`uncertain` 的渠道事实不可改写、不可自动重发，运营只能通过受权限和审计保护的动作记录“已人工核查”；只有未核查终态继续阻断 readiness。Prometheus 与日志只保留聚合数量。
- 服务时长约束、用户完成确认、工单负责人约束、工单结论回显、订单生命周期审计。
- 普通未结工单按用户设置并发上限并在数据库 advisory lock 下计数，避免刷单式工单淹没客服；`safety` 紧急通道不受普通上限阻断。
- 商用模式拒绝缺少 `clientRequestId` 的新订单；小程序按预约业务参数持久化模糊网络结果的请求键，重启后继续复用，收到成功响应才清除。跨副本事务锁同时执行全局未结订单、单用户活跃订单和单陪伴者待响应队列上限，并由 `ORDER_MAX_SCHEDULE_DAYS` 限制预约占位周期；即使紧急关闭新单，同键重试仍会返回已存在的原订单。`ORDER_INTAKE_ENABLED` 与 `PAYOUT_CLAIMS_ENABLED` 是生产显式硬开关，事故时可在不破坏存量履约/凭证补录的前提下暂停新订单或新结算领取。
- 改期先落为一条独立、可审计的协商请求：客户或陪伴者可在未确认待支付或已支付但未开始的订单上提出一个经过当前时段和容量校验的候选时间；提出请求不会改写原预约、支付、退款或履约状态。请求在 `ORDER_RESCHEDULE_RESPONSE_WINDOW_MINUTES`、未确认订单的确认时限与原预约可开始时点之间取较早失效点，生产环境须配置 `rescheduleRequested`、`rescheduleAccepted`、`rescheduleRejected`、`rescheduleExpired` 与 `rescheduleCancelled` 订阅消息模板；接受时在独立事务中再次校验时段和容量后，才会更新预约快照，拒绝时只关闭协商请求并保留原预约。小程序只在用户主动点击订单提醒后按角色请求这些模板；由于微信单次最多展示三项，客户端会分批记录授权，未授权时订单内时间线仍是事实来源。`ORDER_RESCHEDULE_EXPIRY_*` worker 会批量扫描到期协商，并以订单、请求的同序行锁和幂等通知事件键让多副本只完成一次过期闭环；开关可在事故处理中显式暂停，支付/退款对账不受影响。客户取消订单、陪伴者拒单、退款请求持久化、服务开始或服务完成时，同一事务会撤销未决协商，防止后续改期接受复活已取消、已退款、退款进行中或已履约的订单；完成态的检查还覆盖历史数据和异常状态迁移留下的请求。
- 昵称、陪伴者申请/自助/后台发布资料和评价均在服务端本地规则识别和必要人工复核后才可公开；不通过的内容创建审核工单并失败关闭。当前版本的 provider 边界拒绝任何用户原文，生产必须显式设置 `EXTERNAL_AI_USER_CONTENT_ENABLED=false` 且不得保留 `DEEPSEEK_API_KEY`。未来外部内容处理方只有在新版隐私文本与适用的 PIA/DPA、地域、留存、禁止训练和接收方审查完成后才可设计接入，代码不能代替法律签字。社区拒绝客户端外链封面，在合规存储与媒体审核适配器接入前不允许以 URL 绕过媒体门禁。
- 法律文本在应用接受流量前按版本、内容哈希和 HTML 强制归档；同一版本内容漂移会导致启动失败，当前后端商用文本版本为 `2.2-2026-08-01`，已加入本地内容安全边界和腾讯 TRTC 第三方处理披露。小程序后端地址、法律链接和同意版本与生产配置不一致时，部署预检失败。
- 低风险通知、订阅授权和过期刷新令牌由 `LEGAL_PRIVACY_RETENTION_DAYS` 驱动清理；交易、客服、审核与同意证据按经批准的分类留存表处理。到期的受限保留记录也以持久 phase/cursor、租约和有界批次执行，失败不会伪装成已经删除。
- 账号注销在未决支付、退款、工单和法定保留义务清零后，仍须由不同人员双人批准。批准只会排入分阶段擦除任务；worker 以数据库租约、多副本安全领取、每表有界批次和独立提交推进，持久化 phase/cursor/失败/退避。只有全部最终后置条件通过、保留台账已固定后，才可完成请求并封禁原账号；后台显示进度、失败和受审计重试，不能手工跳阶段或把排队写成已删除。
- 管理后台“商用运营门禁”汇总退款政策未批准、订单退款快照缺口、微信配置起始日起所有应核日期 × 四类账单覆盖、全部历史开放差异、待独立复核提案、成功交易渠道时间缺失、失败/超时退款、超时工单、支付投诉超时/同步失败、通用通知关闭但有积压、投递 SLA 超时、未被站内已读兜底的失败推送、过期推送租约、可约提醒各阶段失败/过期租约/SLA 积压/未核查终态、账号注销执行与保留到期积压、待复核档案、未结追偿、超时结算任务、严重/超时内容审核、媒体审核或到期删除失败、过期支付、预约响应/支付保留超时、已过履约窗口待退款和超时服务订单；用户读到事务性站内通知后只关闭沟通缺口，不会篡改原微信失败记录。
- 每个受保护请求都从数据库读取当前账号状态和角色：降权立即生效；普通用户 `restricted` 只读、`banned` 禁止普通业务，但仍可进入退出登录、协议撤回、账号动作/申诉，以及政策允许的访问、导出、更正、删除申请与状态等最小法定自助入口；管理员或审核员一旦不是 `active`，连只读后台数据也不可继续访问。

## 对外开放前的 P0 签字项

以下任一项未完成，结论均为“不放行”，不能通过修改文案或环境变量绕过。

- 经营与法律：确认经营主体、服务类目、用户协议、隐私政策、平台规则、退款/迟到/爽约规则、陪伴者合同、投诉渠道、发票和税务处理；退款规则必须取得可追溯、非秘密的版本批准引用，并与支付前展示的版本和小时数一致。由合资格顾问确认个人信息、算法推荐、内容治理、未成年人及交易记录义务，并确认“线上陪伴而非心理治疗/医疗服务”的产品边界、页面表达和人员话术。
- 内容安全：当前版本确认用户原文仅由本地规则和授权人工复核处理，完成规则版本、人工复核 SLA、夜间值班、申诉和紧急风险升级签字；为自伤、人身危险和急性医疗场景制定按服务地区校验过的危机 SOP、当地紧急资源、升级联系人和演练记录，不能把规则命中或系统提示当作已经完成救助。规则引擎不等同于人工团队、法律或危机运营验收；未来启用外部处理方必须重新完成数据处理安排和法律门禁。
- 微信：小程序主体、类目、隐私接口、业务域名、ICP备案、商户号绑定、JSAPI 支付、退款权限、支付通知地址、消费者投诉 2.0 通知地址和全部必需事务消息模板（含 `messageReceived`；若显式启用可约提醒投递还含 `availabilityReminder`）均已真实审批，并保留截图/工单编号。投诉通知地址必须在商户平台独立登记；代码和环境变量不能替代这一外部配置。
- 身份与证据：接入真实 KYC/签约/税务/收款对象系统或加密证据库；仓库字段只保存外部引用，不得在后台 JSON、审计元数据或环境变量中存证件、银行卡原文。
- 财务：确定平台费率、结算主体、发票/代扣安排、微信日账单对账、退款差异账、追偿和坏账审批；批准每日拉账与差异处置 SOP，并提供可追溯的 `WECHAT_DAILY_BILL_RECONCILIATION_APPROVAL_REFERENCE`。规模化前应以受监管的付款提供方替代人工带外转账；人工模式只允许在已批准的低容量和双人值班上限内运行。
- 运维：独立生产数据库与 Redis、TLS、最小权限、密钥轮换、集中日志、跨副本监控、告警、加密异地备份、恢复演练、容量测试、值班和安全事件响应均有实际验收记录。
- 无障碍与弱网：用微信真机的屏幕朗读、字体/显示放大、焦点顺序、非颜色提示和触控目标走完支付、举报、争议与数据权利关键路径；同时覆盖低端机、弱网、断线和重试。代码审查或供应商自述不能替代真机证据，也不得在无证据时承诺无障碍等级。
- 真实链路：在隔离 staging 完成微信登录、订阅授权、确认后支付、重复/乱序回调、取消、服务、退款成功/失败/重试、工单冻结、结算双人复核、追偿和账号注销；生产只做一笔受控真钱验收，不允许自动化使用生产商户或生产 Redis。
- 历史数据：迁移只可根据既有完整小时截止时间确定性写入 `legacy-inferred-v1`，其余记录明确写入 `legacy-72h-v1`；这只是技术兼容标记，不代表政策已经批准。逐笔处置历史 `paid`、`inService`、`completed`、失败退款、未结工单、退款快照缺口及无收款快照的结算记录。历史订单不得自动补造成“已完成商业核验”。

## 放行步骤

1. 复制 `backend/api/.env.production.example` 到保密配置，填写真实值；配置 `COMMERCIAL_RELEASE_MODE=commercial`、经批准费率、`REFUND_POLICY_VERSION`、`REFUND_POLICY_APPROVED=true`、非秘密 `REFUND_POLICY_APPROVAL_REFERENCE`、退款期、结算期、订单容量和订单/结算硬开关。生产示例故意保持退款政策未批准；没有真实外部批准不得把它改为 `true`。每日账单必须设置 `WECHAT_DAILY_BILL_RECONCILIATION_ENABLED=true`、`WECHAT_DAILY_BILL_RECONCILIATION_APPROVED=true`、非秘密批准引用、经财务确认且不晚于最新可取账期的 `WECHAT_DAILY_BILL_RECONCILIATION_START_DATE`，以及 10–23 点的上海时间执行小时；没有真实财务批准或起始日期时示例配置会故意保持 No-Go。另将 `COMPANION_VOICE_EVIDENCE_VIEWER_URL` 指向外部 HTTPS 受控查看器，并用独立 32+ 位密钥签发 60–900 秒的管理员试听地址；查看器未配置或不可用时，语音介绍批准必须保持 No-Go。容量必须来自当班运营、客服和财务真实承载能力，不能照抄示例。
2. 在生产部署前执行：

   ```sh
   cd backend/api
   npm run preflight:deployment -- .env.production
   npm run verify:prod-artifacts
   npm run prisma:deploy
   ```

3. 先访问并核对 `/api/v1/legal/terms`、`/api/v1/legal/privacy`、`/api/v1/legal/platform-rules` 及小程序使用的 `/legal/*.html`，确认版本快照已经创建且旧版本可访问。
4. 签发一个短时 admin access token，与 `METRICS_TOKEN` 一并只通过当前 shell 环境传入，运行 `scripts/production-smoke.sh https://真实域名`。脚本会核验用户内容保持本地处理、`externalUserContentTransmission=false`，并要求商用运营门禁为 `clear`；它不会向 DeepSeek 或其他外部生成式 AI 发送探测文本。随后完成一笔受控真钱订单，核对微信账单、订单、支付、通知、退款、应结款、审计和客服记录。执行后立即撤销 token 并清理 shell 历史。
5. 管理后台 `/admin/commercial/readiness` 必须为 `clear`；外部 P0 签字项、迁移备份和回滚负责人齐全后，由产品、工程、运营/客服、财务和法律/合规共同签署 Go。

## 可约提醒的受控放行与异常核查

默认保持 `AVAILABILITY_REMINDER_DELIVERY_ENABLED=false`。首次开放前，先在隔离 staging 用一个测试账号完成“明确授权 → 开启私人书签偏好 → 新建真实可约时段 → provider 接受”的完整演练，并确认以下条件：

- `npm run preflight:deployment -- .env.production` 通过；若开关为 `true`，预检必须同时看到 `WECHAT_SUBSCRIBE_MESSAGES_ENABLED=true` 和唯一、已审批的 `availabilityReminder` 模板。
- `/api/v1/metrics` 的 `talk_availability_reminder_delivery_success_total`、`talk_availability_reminder_delivery_failures_total` 与 `talk_availability_reminder_delivery_skipped_total` 已由内网采集；初次小流量期间，任何 failure 或 `uncertain` 增量都由当班工程师人工核查并记录处置结论。
- 核查数据库时只能使用受控的只读账号、只取聚合状态，不可导出尝试 ID、用户 ID、授权或 provider 消息号。例如：

  ```sql
  SELECT "status", "outcomeReason", COUNT(*) AS "count"
  FROM "AvailabilityReminderAttempt"
  GROUP BY "status", "outcomeReason"
  ORDER BY "status", "outcomeReason";
  ```

- 异常时先把 runner 开关改回 `false` 并保全日志、指标和审计证据。不得手工释放已消费授权、改写尝试状态、删除租约，或重新启用 runner 来“补发” `uncertain`、`rejected`、`failedBeforeSend` 或任何旧租约；只有新的 `reserved` 尝试才可在后续受控运行中进入发送边界。

这不是面向客户的投递状态页、客服补发工具或外部告警写回机制。它只定义部署责任人与值班工程师的最小人工核查边界，订单、退款、结算和用户消息仍完全独立。

## 日常停机红线

出现支付/退款对账不平、失败退款无人处理、身份或收款对象证据失效、追偿逾期、备份不可恢复、关键告警失联或疑似数据泄露时，立即暂停新订单、上架和人工付款。先保全支付通道、数据库、审计与工单证据，再逐笔处置；不得删除财务表、回滚枚举或批量重发结果不确定的一次性微信消息。
