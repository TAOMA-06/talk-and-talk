## Candidate, CI, artifact, rollback, and G2-ready work

`QA-02` can generate a local candidate-capture subset from a clean frozen
checkout. It records full candidate and parent SHA, branch, clean status, UTC
timestamp, Node/npm/OS/tool versions, command logs and hashes, reviewer
reference, and tree hashes for lockfiles, OpenAPI, migrations, critical
configuration, Web build output, Mini release source, generated Prisma/API
`dist`, static assets, and a format-checked SBOM. An OCI image digest is
recorded only if an image is actually built. The local files are not immutable
custody, authenticated execution, authorization validation, or dependency
provenance evidence; those facts require external references and independent
review.

The local capture tool runs only allowlisted Web/Mini/API/static gates and
`git diff --check`; it cannot launch E2E/Docker. Browser evidence, remote CI,
migration-forward-upgrade, rollback drills, custody, and scenario execution are
separate records. The future control-plane dispatch must originate from a
separately protected immutable control ref/repository, verify that control
identity before checking out the requested candidate into its own path, and
keep candidate execution socketless and outside the control-plane mount. The
candidate tag alone must never define the workflow or runner policy. G1 needs two consecutive
zero-failure, zero-skip isolated E2E runs plus an empty-database migration and
forward-upgrade check. A skipped DB test is a blocker, not a pass.

The rollback record pins a prior approved SHA and artifact identifiers, declares
forward-compatible migration and backup/restore steps, and exercises rollback
only in the disposable environment. It separately rechecks
`WEB_SURFACE_MODE`, `COMMERCIAL_SURFACE=text_only`, and media/TRTC disablement.
The execution template in `g2-execution-package.md` must be populated and
independently reviewed before the label `G2-ready` can be used. G2 itself
remains blocked.
