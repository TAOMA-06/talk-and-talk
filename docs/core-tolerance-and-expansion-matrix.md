# Talk&Talk 核心宽容度与拓展度决策

> 决策日期：2026-07-25  
> 决策视角：技术负责人 + 商务负责人  
> 当前发行范围：微信小程序 + NestJS 后端；历史 iOS 工程不参与商用放行

## 1. 这里的“宽容度”与“拓展度”

- **宽容度**：某个依赖、功能或体验暂时不完美时，产品仍能诚实履行核心承诺的范围。宽容不是静默造假，也不是用旧数据假装新能力可用。
- **硬边界**：一旦越过就必须失败关闭、暂停流量或转人工的范围。资金、安全、身份、真实容量与隐私不采用“先跑起来再说”。
- **拓展度**：已经预留、但只有在用户价值、单位经济和运营能力出现证据后才启动的扩展方向。技术上能做，不等于现在应该做。

首发唯一核心承诺是：**用户看到的是当前可买、可约、可在平台内履约并可售后的线上陪伴服务。**

## 2. 董事级结论

1. 先做供给密度、履约稳定和复购，不把社区活跃或下载量当成第一增长目标。
2. 商用订单不再接受“资料标价 + 自由填写时间”的新单。旧字段只保留内部兼容和历史读取。
3. 默认发现与推荐只展示未来 7 天内同时具备有效商品和真实剩余容量的陪伴者。
4. 评分、评价数、完单数和响应时间属于交易事实，不属于运营文案；后台也不能直接改写。
5. 首发以文字服务为默认交付方式。语音仅在 TRTC、主体类目、真机、关房和应急清场全部通过时开放。
6. 暂不扩展 iOS 首发、陌生人泛社交、群聊/群语音、视频、虚拟币、多支付渠道、AI 陪聊或医疗化能力。
7. 所有增长判断以订单事实漏斗为准：请求、接单、支付、准时开始、完成、评价、退款、复购与净实收。

| 核心部分 | 首发承诺 | 可宽容范围 | 零宽容边界 | 可拓展方向 | 扩展触发器 / 决策人 |

| 可约与容量 | 用户选择结构化时段；下单、接单、支付前重复校验容量 | 时段瞬时被占可返回明确冲突并刷新；旧自由文本时段可展示为历史说明 | 商用新单不得用自由文本时段或目录故障降级成交；不得超卖 | 周期排班自动发布、候补、动态容量、外部日历 | 未来 7 天有持续供给且人工排班成为主要运营成本；供给运营 + CTO |
| 发现与推荐 | 默认只返回未来 7 天真实可售对象，并展示商品起价、时长、方式和下一可约时间 | 推荐服务故障可退回同口径公开目录；个性化关闭时可用非个性排序 | 不可把未发布、未核验、无 SKU、无容量或语音已停用对象放入立即可约结果 | 供需平衡、探索位、主题召回、候补召回 | 每个实验有支付/完成而非点击指标；产品 + 商务。规模触发后才建设物化可售索引 |
| 下单 | 同一用户动作只创建一单；商品、时段、价格、证据全部快照 | 网络超时可用同一幂等键找回；内部模式可读取旧单 | 商用模式缺少 `clientRequestId`、`serviceOfferingId` 或 `availabilityWindowId` 必须拒绝 | 购物车、多服务组合、赠礼、企业采购 | 单服务订单已稳定且新模式有清晰履约与退款归属；商务 + 财务 + CTO |
| 支付 | 服务端预下单、回调/查询确认、金额一致、可对账 | 用户取消支付、回调延迟或状态未知可保持待确认并主动查询 | Mock 支付不得进入生产；金额、商户单号或回调验签不一致不得落账 | 第二支付渠道、余额、分期 | 微信渠道对收入形成真实限制，且新渠道对账/退款/合规成本获批准；财务 + CTO |
| 履约 | 订单参与者在购买窗口内平台内沟通；按预约开始与完成 | 聊天通知可延迟，历史仍可读；文字服务可在语音关闭时继续 | 未支付、非参与者、服务窗口外不得继续普通消息或入房；完成时间不得提前 | 实时语音、视频、结构化服务脚本、质量抽检 | 语音外部门禁全部通过；视频需另做安全、审核、带宽和主体评估；运营 + 安全 + CTO |
| 信任与评价 | 公开评价来自已完成订单；评分、数量、完单数、响应时长由事实派生 | 样本少时显示“暂无履约数据/新陪伴者”；不强行给精确排名 | 运营、陪伴者或管理员不得手工制造信任数字；私密体验反馈不得公开 | 已购标签、准时率、复购率、分场景质量 | 每项指标有最小样本、反作弊和解释文案；产品 + 数据 + 合规 |
| 售后与退款 | 订单内发起、状态可见、成功以支付提供方确认为准 | 复杂争议可进入人工；处理慢时保留证据并明确状态 | 退款状态未知不得当作成功；退款不得绕过结算冻结与双人资金控制 | 自动规则、分段退款、服务信用补偿 | 争议类型稳定且人工结论一致性足够高；客服 + 财务 + 合规 |
| 结算与追偿 | 完成后等待退款窗口，使用订单不可变证据快照结算 | 证据缺失、退款异常或追偿未结可长期 hold | 不得用今天的资料重建历史收款证据；付款与复核职责分离 | 受监管批量付款方、税务自动化 | 人工结算接近已批准容量上限或出现错误风险；财务 + 合规 + CTO |
| 通知 | 通知是提醒，不是交易事实；一次性授权只消费一次 | 通知失败不回滚已提交订单；用户可从订单内查看真实状态 | 结果未知不得自动重发一次性模板；不得泄漏另一方私有状态 | 生命周期触达、召回、经营通知 | 先证明通知提升完成率且退订/投诉可控；产品 + 运营 |
| 社区 | 只保留受审核、可举报的轻量内容入口 | 活跃低、内容少可接受，不以假数据填充 | 不允许社区绕过交易、聊天窗口、未成年人和内容安全边界 | 主题沉淀、服务相关内容、低压互动 | 核心交易完成率和安全值班稳定后；CEO/商务 + 安全。当前不做群聊、匿名大广场或群语音 |
| 渠道与客户端 | 微信小程序是唯一商用客户端 | 历史 iOS 可作为代码参考，不参与发布验收 | 不允许两个客户端对价格、权益、退款或安全边界采用不同规则 | iOS、Web、企业端 | 至少 300 笔已完成付费订单、复购有稳定证据，且新渠道有独立获客价值；CEO + CTO |

## 5. 经营漏斗与指标口径

后台 `GET /api/v1/admin/commercial/funnel` 以订单创建时间形成 cohort，不读取或返回聊天内容与客户身份。

| 阶段 | 当前事实口径 | 决策用途 |
| --- | --- | --- |
| 请求 | `Order.createdAt` 在区间内 | 真实交易意图 |
| 接单 | 当前 `companionConfirmedAt` 存在，或订单确认事务留下 `order.companion_confirmed` 不可变审计事实 | 供给响应；支付保留到期后即使当前确认字段被释放，仍保留已接单事实 |
| 支付 | `paidAt` 存在 | 成交 |
| 应开始 | 已支付且预约时间已到 | 排除未来订单，作为开始率分母 |
| 准时开始 | `serviceStartedAt <= scheduledAt + 5 分钟` | 履约可靠性 |
| 应完成 | 已支付且预约时长已结束 | 排除尚未到期订单 |
| 完成 | `completedAt` 存在 | 可交付收入 |
| 评价 | 完成订单存在公开评价 | 信任供给 |
| 退款 | 存在成功退款交易 | 质量和净收入风险 |
| 复购客户 | 区间内付费客户有历史付费或区间内至少两单 | 价值留存 |
| 净实收 | 已支付金额减成功退款金额 | 当前经营贡献，不等于会计确认收入或利润 |

推荐后台指标同步扩展到接单、支付、开始、完成、评价、退款和归因 GMV。曝光、查看、点击只能用于诊断，不能作为业务成功结论。

## 6. 放量阶段与停止规则

这些阈值是首发经营政策，不是自动修改资金或订单的代码规则；每周由商务、运营、财务和工程共同复核。

### A. 受控试运营

- 上限：20 名已核验陪伴者、累计 100 笔已支付订单；不做公开大规模买量。
- 必须：支付/退款逐笔对账、客服有人值班、后台 readiness 为 `clear`、语音默认关闭或已完成全部外部验收。
- 任一 P0 安全事件、金额不一致、未解释的重复扣款、无法追溯的退款/结算，立即暂停新单。

### B. 小规模增长

在至少 30 笔“应开始”订单和 30 笔“应完成”订单后，同时满足：

- 准时开始率不低于 90%；
- 完成率不低于 90%；
- 成功退款订单率不高于 10%，且原因已分类；
- 支付、退款、结算对账无未解释差异；
- 客服与审核积压不超过已批准值班容量；
- 供给在未来 7 天持续有真实可售时段。

未达标时优先修供给和履约，不扩大营销。

### C. 规模化

累计至少 300 笔已完成付费订单、复购开始形成稳定 cohort、单位经济经财务确认后，才评估 iOS、新支付渠道、自动化结算、数据仓库或更复杂的推荐。任何一项都是独立立项，不捆绑“大版本”一起上线。

## 7. 本轮已完成的纠偏

| 原问题 | 已完成决策与改动 |
| --- | --- |
| 公开/推荐会展示买不到的人 | 默认目录、排序和推荐共用“有效 SKU + 未来 7 天结构化剩余容量”的可售读模型；语音关闭时默认只保留文字供给 |
| 商用新单仍能走旧资料价/自由时间 | 商用模式强制幂等键、商品 ID 和时段 ID；小程序目录或时段故障时失败关闭，不再降级创建旧版订单 |
| 卡片价与成交价口径分裂 | 发现、社区相关和订单后续推荐统一展示当前可售 SKU 起价、时长、方式和下一可约时间；按价格排序也使用当前 SKU。私人书签/最近浏览不再展示旧资料价 |
| 信任数字可由后台制造 | DTO 拒绝直接写评分、评价数、完单数和响应时间；评价、完单和接单事实更新派生指标，并提供历史校准迁移 |
| 经营层只看到曝光和点击 | 新增隐私安全的商业漏斗；推荐指标也延伸到接单、支付、履约、评价、退款和归因 GMV |
| 文档仍暗示 iOS 属于当前发行 | 总指引和契约改为微信小程序 + NestJS 的唯一当前范围 |

## 8. 明确保留的风险与下一步

1. `20260725100000_derive_companion_trust_metrics` 会重算现有公开信任字段。生产执行前必须备份，并先在 staging 对比每位陪伴者的评价、完单和响应结果。
2. 本轮已通过编译、单元/冒烟和契约类门禁，但没有替代真实 Postgres/Redis、微信支付、微信真机、订阅消息和 TRTC 外部验收。
3. 商业漏斗和推荐归因已共用“当前确认字段 + 不可变接单审计”口径。极早期未产生该审计、又已释放确认字段的历史/人工导入订单仍可能低估；staging 校准时应单列，不应人工伪造接单事件。
4. 经营漏斗单次最多读取 10,000 个 cohort 订单、最长 90 天；超过这一规模时转为异步聚合/仓库，不把在线数据库当 BI。
5. 可售扫描适合当前早期规模。候选量和 SKU/时段增多后，应依据延迟与数据库负载建设物化可售索引，而不是提前引入复杂搜索基础设施。
6. `companions.service.ts`、`orders.service.ts` 等领域服务较大。短期保持小步修改和测试保护；团队并行冲突成为实测问题后，再按目录、容量、交易、履约、财务拆分。
